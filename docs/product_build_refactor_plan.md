# 多产品构建重构计划

状态：规划中，尚未开始实现。日期：2026-10-09。

工作分支：`refactor/product-build-pipeline`，从 `master` 的 `ad96fdd8` 创建。
本文件是本轮实施和决策记录；旧 `tmp/jar-patch-refactor-plan.md` 不作为本轮待办。

## 1. 目标与边界

同一份源码通过明确的产品配置生成标准、宋体、综艺体、启动优化四种汉化产品，
不再依赖产品分支之间反复 rebase。构建从固定输入生成独立目录，经验证后才能打包、部署。

纳入：产品配置、补丁与运行时装配、构建目录隔离、打包输入、产物验证、部署与回滚、
生成 Jar 的发布方式、旧产品分支退出日常维护。

不纳入：

- 翻译定位算法、词条 key、occurrence 规则、映射格式和翻译校验规则重构。
- 修改译文、重排常量池、改变具体 Patch 的字节码语义或增加新优化。
- Linux/macOS 迁移、升级游戏版本、升级 Java 字节码目标、历史 0.97 分支维护。
- 本轮未批准的运行时/资源精简，或顺带重构根目录无关脚本。
- 文件浏览服务仓库的重构；用户已明确后置，不阻挡本次迁移。

允许对 ParaTranz 做必要的路径传递和调用边界调整，让原有导入/导出逻辑在指定目录运行。
不能以此为由改造上述定位、key 或校验语义；遇到必须扩大范围的情况先确认。

## 2. 已确认的设计决策

| 编号 | 决策 | 约束 |
|---|---|---|
| D01 | 四种产品全部纳入 | 先标准与启动优化，再宋体与综艺体 |
| D02 | 正式支持四个固定配置 | 保留开发开关，不承诺所有自由组合可发布 |
| D03 | 先保持默认游戏产物一致 | 冗余 helper、资源和禁用功能的产物精简单独评审 |
| D04 | 最终不在源码分支跟踪生成 Jar | 过渡期保留；四种产品构建、打包、恢复通过后转至 Release |
| D05 | 完成后直接切换新流程 | 不建设长期兼容层；旧版本及分支只作归档 |
| D06 | 文件浏览服务适配后置 | 记录接口变化，不修改该仓库、不触发其更新作为验收步骤 |
| D07 | 全程在独立分支实施 | 当前 master 和三个产品分支保持可用，最终验收后才整合 |
| D08 | 排除翻译定位/key 重构 | 只调整输入输出路径和编排，不做平台词条迁移 |

旧流程在开发期间仍可使用，不等于最终继续维护两套入口。
版本查询 URL 与文件浏览服务区别处理：前者影响玩家更新检查，需要在最终切换时有明确去向；
后者可以等本轮完成后再适配，不要求旧索引在迁移后继续自动更新。

## 3. 当前基线与已知耦合

| 产品 | 基线提交 | 主要差异 |
|---|---|---|
| 标准版 | `ad96fdd8a5dbaad9f3197bb9fe17cc1ef20fa5f9` | 15 个基础汉化 Patch |
| 宋体版 | `d8ebc6486f3f110ae430f50e484e758618dc7a86` | 三套字体描述与图集、版本元数据 |
| 综艺体版 | `26928b9a5cc437d110e1de3f0bd97f8bdc1434ce` | 三套字体描述与图集、版本元数据 |
| 启动优化版 | `d5c4e6ac876f7129b4155c0399b0494de7b6b92b` | 输入法、动态字体、优化与 profiling；注册 70 个 Patch，含非默认 profiling |

这些是规划基线，实施前需保存文件和 Jar entry 哈希。若主线继续更新，按第 8 节重新登记。

已核实的耦合：

- 两个 Java 分支已经共享 `JarPatch`、`PatchSelection`、`PatchGroupKind`、`JarRewriter`；
  不重复实施 8 月 31 日已完成的公共框架移植。
- Patch 选择、运行时注入、DLL/字体分发仍分别存在于 Java 注册表、Main、Python 构建代码。
- `JarWorkspace.writeOutputs()` 会更新 `original/` 和 `localization/`，后者可能暂时成为未翻译状态。
- ParaTranz 多处在模块导入时绑定路径和映射；不能靠入口临时覆盖几个全局变量实现目录隔离。
- 打包工具固定读取 `localization/`，并从 Git 分支名推断产品；Inno 脚本也存在固定源目录。
- 生成 Jar 与源码一起重放历史提交，造成反复二进制冲突。
- 分支间的 ParaTranz JSON 存在上下文编号差异；迁移前分类确认，不擅自合并或重写词条。
- 当前测试游戏关闭 JVM 字节码校验；游戏能启动不能替代开启校验的产物验证。

## 4. 目标结构与数据流

保留现有工具边界：Java 负责补丁计划与字节码变换，Python 负责流程和文件装配，
ParaTranz 负责原有翻译操作，packaging 负责安装包。配置与依赖环境放各自工具目录，
不在仓库根新增全项目 Python 环境或无关的格式检查范围。

建议布局（具体文件名在相关阶段确定）：

```text
jar_pre_processing/
  profiles/                 四个发行配置，显式列出功能
  assets/                   按产品分类的受管理资源及依赖清单
  src/                      公共 Patch 框架与所有产品实现
  build.py                  构建编排入口
  build/<profile>/<id>/     隔离的阶段输出、报告与成功产物，不入库
para_tranz/                 现有映射、译文快照与脚本
packaging/                  消费已验证的产品目录及构建清单
```

阶段流：

1. 固定原版输入、源码、产品配置、映射、译文快照及工具/依赖版本，检查内容哈希。
2. 生成构建计划：功能集合、Patch 顺序、运行时、第三方库、native 与字体资源。
3. 在 staging 中运行 ASM Patch → 字符串解耦 → 所需运行时注入。
4. 按现有语义应用固定译文快照，装配非 Jar 文件与产品资源。
5. 验证完整文件树、Jar entry、翻译结果和产品边界，生成最终清单。
6. 验证全部成功后标记为可打包/部署的产物；失败目录不能冒充成功产物。

执行要求：

- 默认构建不下载平台最新译文、不访问平台写接口，不修改输入快照。
- 发布以干净输入重建；不复用上次的汉化 Jar。日常平台同步与发布构建分开。
- Java 是功能依赖、补丁顺序和选择校验的唯一实现；Python 消费计划，不重复维护依赖图。
- 功能定义关联 Patch 与所需 runtime/资源；共享资源集中声明，避免重复复制和冲突版本。
- 用户功能依赖仍严格校验，不悄悄补齐；被选功能所需的装配资源由计划完整列出。
- 明确区分功能依赖、Patch 顺序约束和不兼容组合。先校验并保留现有执行顺序，
  不在迁移中引入会改变产物的自动重排。
- 正式产品使用明确的功能清单，新增优化不会因 `all` 自动进入发行配置。
- 默认产品迁移期保留原有 runtime 集合；即使发现多余类，也不能在架构提交中删除。
- 两个分支对同一个 Patch 的既有实现差异必须单独登记；以按产品选择的实现或明确参数
  保留原行为，不能直接用优化分支版本覆盖标准版。例如日期栏补丁还包含优化版的换行处理。
- 标准版不得携带启动优化、输入法、动态字体实现；profiling 只出现在显式诊断构建。
- 构建清单区分可复现输入信息与时间/本机路径等运行记录，不要求不同机器、不同原生
  工具链天然生成相同二进制；预编译 native 与字体包先作为带哈希的固定输入复用。
- 新目录装配时必须核清静态资源与翻译生成文件的来源；缺少所需词条不得默默拿旧汉化
  Jar 或旧构建结果补齐。既有空文件/跳过规则保持原语义并在清单中显式说明。

每阶段补上该阶段的行为测试；P10 是矩阵汇总与 CI 接线，不是到最后才开始测试。

## 6. 验证与验收标准

### 基线一致性

- 每种产品单独比较，不把优化版与标准版互相比作“无差异”。
- Jar 比较 entry 名、解压后字节、class 版本与必要的常量池/译文定位回归；
  ZIP 时间戳、权限和压缩封装差异单独记录，不算游戏语义变更。
- 非 Jar 游戏文件默认逐字节一致；只允许预先列明的产品元数据变化和构建报告新增。
- 平台 key、原文、译文、stage 和映射保持原状。分支已有的上下文编号差异单独核对，
  不通过导出覆盖共享快照“消除”差异；若不能在既有语义下兼容，停止并提问。
- 导入/导出只在临时工作区进行；不上传词条、不修改本地译文以通过校验。

### 测试矩阵

| 层次 | 必须覆盖 |
|---|---|
| 计划 | 四个固定配置、显式开发配置、未知/重复 ID、缺依赖、禁用冲突、顺序环、不兼容组合 |
| 流程 | 缺输入、错误游戏版本/哈希、翻译校验失败、编译失败、缺 native、残留构建目录、打包拒绝失败产物 |
| 产品边界 | 标准不注入优化 runtime；字体覆盖精确；profiling 默认关闭；共享依赖仅装配指定版本 |
| Java | 现有主线及优化回归；JDK 17 与 25 的相关校验，明确编译目标仍为 Java 17 |
| 字节码 | 有完整游戏依赖的隔离 JVM 开启验证，覆盖受修改类/方法及解耦回归；不以 ASM 检查代替真实 JVM |
| ParaTranz | lint/format/type check、单元/集成测试、固定快照导入导出对比、路径隔离；不改 key 测试预期掩盖回归 |
| 重建 | 相同固定输入重复构建，游戏 entry/文件一致；干净克隆不依赖本机忽略文件 |
| 打包 | 四产品独立 ZIP/EXE；完整包复用原版完整性校验；保留设置的安装行为不变 |
| 部署 | 相同产品重复部署、优化版与标准版互换、备份恢复、部分写入失败；不删除 Mod/存档或任意未知文件 |
| 游戏 | 四产品启动、读档、基础中文界面；优化版另验输入法、动态字体、相关优化和存取档 |

CI 中先运行不依赖游戏和私有输入的测试；需要原版游戏、字体或本机图形界面的验证使用
明确准备的受信输入/本地环境，不能让 CI 缺输入时静默跳过后宣称完整验收。
现有 ParaTranz 集成测试依赖 `original/starfarer.api.jar`；停止跟踪它之前，必须接通
测试输入的构建或经哈希验证的准备步骤，并使干净克隆下的测试命令有明确、可执行的前置流程。
未知验证器限制、现有类加载问题或已有游戏错误要单独记录，不宽泛禁用验证来通过。

## 7. 风险、回滚和停止条件

- 资源来源：TTF 等忽略文件可能只存在本机。先验证固定预编译字体包可用，登记获取、
  哈希及源码重建条件；本轮不把“能在当前机器构建”当作干净环境可复现。
- 运行时集合：功能描述接管装配时可能改变注入范围。默认产物不一致先定位，不能顺便精简。
- 全局路径：禁止并行构建共用可变全局路径、靠重载模块切目录、跨进程抢写同一输出。
- 输入固化：构建运行期间不得被平台下载或人工修改替换输入；使用独立快照并记录哈希。
- 部署：Windows 多文件覆盖不是整体原子事务；用完整备份、状态记录和恢复流程处理，
  不承诺单个 rename 能完成全部切换。检查游戏关闭后再操作其文件。
- 跨产品残留：只清理旧安装清单证明属于本工具的文件；必要缓存按格式/版本检查失效，
  不把用户自定义字体字表、设置、Mod 或存档当作可删除产物。
- 发布：停止 Git 跟踪之前必须有可取回的旧版与新产物；不重写 Git 历史去清除旧二进制。

任何意外 class/译文变化、需要修改定位算法、无法解释的旧分支差异、必要资源缺失，
都暂停相关阶段并提供证据与选项。无关旧告警记录基线，不降低现有校验规则。
回滚以阶段提交和固定基线为单位；不得手工拼接上下游 Jar 或移植 class 条目。

## 8. 分支、上游更新与交付方式

- 所有实现和计划更新只进入 `refactor/product-build-pipeline`；不直接修改四个现行产品分支。
- 当前只建立分支、完成调查与计划。未授权提前合并主线、推送、发布 Release、部署或归档远程分支。
- 需要重跑旧构建时使用隔离 worktree/目录；不在带改动的工作区反复切换产品分支。
- 每阶段报告改动、测试、与基线差异、剩余问题；重要设计选择先确认并写入第 9 节。
